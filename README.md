## 1. 검토 목적

- dSPACE가 제공하는 **모델 기반 개발(MBD) 검증 툴체인**과 유사한 제품을 개발할 때,
  무엇을 만들고(범위), 어디서 차별화하고(전략), 무엇을 조심할지(리스크) 정리한다.
- 결론을 내리기 위한 문서가 아니라, **다음 검토의 출발점**이다.

## 2. dSPACE 솔루션 맵 (요약)

| 계층 | 제품 | 역할 |
|---|---|---|
| 모델링 | ASM, AURELION | 플랜트 모델(엔진·차량·전기구동), 센서용 3D 가상환경 |
| 코드 생성 | TargetLink, SystemDesk | 양산급 C 코드 생성(기능안전), AUTOSAR 설계 |
| 가상 검증 | VEOS | PC 기반 vECU/SIL, 오프라인 시뮬레이션 |
| 프로토타이핑 | MicroAutoBox III | 차량 탑재형 RCP (ARM 쿼드코어) |
| HIL | SCALEXIO (LabBox/OTS/맞춤 랙) | 실시간 HIL 시뮬레이터 |
| I/O | SCALEXIO I/O 보드, 고장 삽입 유닛 | 신호 조건화, 전기적 고장 주입 |
| 설정·자동화 | ConfigurationDesk, Bus Manager, ControlDesk, AutomationDesk, ModelDesk | 설정, 실험, 테스트 자동화 |
| 데이터 관리 | SYNECT | 모델·요구사항·테스트 협업 관리 |
| 특화 솔루션 | EMH(모터), Battery HIL, 환경 센서 인터페이스 | 전동화·ADAS 대응 |
| 프로토콜 | CAN/FlexRay/Ethernet, CANopen, EtherCAT, Modbus, PROFIBUS, ARINC 429/664, MIL-STD-1553, ADASIS, V2X, ROS | 산업·항공·방산 인터페이스 |
| 서비스 | 맞춤 테스트 벤치 구축 | 하드웨어 판매보다 구축·컨설팅 비중 큼 |

**핵심 구조:** 모델 → 코드 → 가상검증 → RCP → HIL → 자동화가 **하나의 툴체인**으로 이어지고,
모델과 I/O 설정을 플랫폼 간 재사용할 수 있는 점이 진입장벽이다.

## 3. 개발 범위 후보 (제안/가설)

전체 툴체인을 동시에 만드는 것은 비현실적이므로 **계층별로 잘라서** 검토한다.

| 후보 | 내용 | 난이도 | 비고 |
|---|---|---|---|
| A. 소형 HIL / RCP 플랫폼 | 고정 주기 실시간 제어 + 기본 I/O(ADC/DAC/PWM/CAN) | 중 | 가장 직접적인 유사 제품 |
| B. FPGA 기반 고속 모터·전력 모델 | 인버터/모터 모델을 FPGA에서 수 µs 주기로 실행 | 중~상 | FPGA 역량이 직접 차별점이 될 수 있음 |
| C. 버스·프로토콜 시뮬레이션 | CAN/CAN-FD, Ethernet, 방산·항공 버스 에뮬레이션 | 중 | 규격 이해와 검증 부담 |
| D. 가상 ECU / SIL 환경 | PC 기반 모델·펌웨어 결합 시뮬레이션 | 중 | 하드웨어 부담이 적어 진입 쉬움 |
| E. 테스트 자동화/설정 SW | 설정 GUI, 시나리오, 리포트 | 중 | 하드웨어와 결합해야 가치 큼 |
| F. 교육용 저가 HIL 키트 | 대학·인력개발기관용 | 하 | 시장 규모는 작지만 진입 쉬움 |
| G. 틈새 도메인 솔루션 | 의료기기, UAS/방산, 산업 장비 | 중 | dSPACE 대비 서비스 중심 차별화 |

## 4. 기술 검토 항목

### 4.1 실시간 실행 환경
- [ ] RTOS vs Linux PREEMPT_RT vs 베어메탈 (지터 요구사항 정의 필요)
- [ ] 목표 모델 주기 (예: 제어 100 µs ~ 1 ms, 전력전자 모델은 FPGA에서 1 µs 이하)
- [ ] 멀티코어 분할, 모델 실행과 I/O 동기화 방식
- [ ] 후보 플랫폼: Xilinx/AMD Zynq·Versal, NXP i.MX, STM32 계열, x86 + FPGA 카드

### 4.2 I/O 하드웨어
- [ ] 아날로그 입출력 정확도·대역폭, 절연, 신호 조건화
- [ ] 센서/액추에이터 전기적 에뮬레이션 (저항·전압 에뮬레이션 등)
- [ ] 고장 삽입(단선/단락/전원 이상) 회로 — **안전·내구성 이슈**
- [ ] 부하/전력단 (모터·배터리 HIL은 고전압·대전류 → 인증 부담)

### 4.3 모델 연동
- [ ] **FMI/FMU** 지원 (필수에 가까움)
- [ ] Simulink 코드 생성 연동 (Simulink Coder 의존 여부)
- [ ] 오픈소스 모델 도구 연동 (OpenModelica 등)
- [ ] 모델 파라미터/데이터 관리

### 4.4 표준·인터페이스
- [ ] **ASAM XIL / XCP / A2L**: 측정·캘리브레이션 호환
- [ ] AUTOSAR 호환 범위 (Classic 우선?)
- [ ] ASAM OpenDRIVE/OpenSCENARIO + CARLA 등 시나리오·센서 시뮬레이션 연동
- [ ] ROS/ROS 2 연동

### 4.5 소프트웨어 구조
- [ ] 설정(GUI) / 실행(런타임) / 실험(계측) / 자동화(API) 분리 설계
- [ ] 테스트 자동화 API (Python 우선 제안)
- [ ] 라이선스·배포 방식, 데이터 포맷 개방 여부

### 4.6 기능안전·인증
- [ ] 목표 고객이 ISO 26262 도구 인증을 요구하는지 확인 (코드 생성 도구 쪽은 부담 큼)
- [ ] HIL 자체는 도구 신뢰성 평가(TCL) 관점 정리 필요

## 6. 차별화 가능성 (가설)

1. **가격/접근성**: 중소기업·교육기관·스타트업이 도입 가능한 가격대
2. **FPGA 기반 고속 모델**: 모터·전력전자·센서 에뮬레이션 특화
3. **틈새 도메인**: 방산 UAS, 항공, 의료기기, 산업 장비 등 자동차 외 영역
4. **국내 지원·구축 서비스**: 현지 언어, 빠른 기술 지원, 맞춤 벤치 구축
5. **개방성**: FMI/Python/ROS 등 개방형 인터페이스 중심
6. **교육 연계**: 교육과정 + 키트 + 실습 환경 패키지

## 8. 단계별 접근안 (제안)

1. **Phase 0 – 조사 (1~2개월)**: 타깃 고객·용도 정의, 경쟁사 실사, 요구 사양 수집
2. **Phase 1 – 최소 검증 (PoC)**: 단일 도메인(예: 모터 제어 HIL)으로 RCP/HIL 소형 시스템 구현
3. **Phase 2 – 소프트웨어 계층**: FMU 연동, 설정/자동화 도구, Python API
4. **Phase 3 – 확장**: 버스/프로토콜 확대, 도메인 솔루션, 서비스화
5. **병행**: 교육용 키트로 소규모 수익 + 사용자 피드백 확보
